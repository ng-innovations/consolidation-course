Trial balance collection & validation

Every consolidation cycle starts with the same task: collect a trial balance from every subsidiary, and verify that what arrived is usable. This is the Ingest phase of the pipeline — steps B.4 (Data Collection) and B.5 (Validation & Normalization).

What a trial balance is

A trial balance is a list of every account in a company's general ledger with its current balance, organized so that total debits equal total credits.

If the trial balance doesn't balance — debits ≠ credits — something is wrong with the local books and the data shouldn't be accepted for consolidation.

How TBs arrive

Subsidiaries submit their TBs in different ways depending on the customer's setup:

  • Direct integration. The system pulls TBs from the subsidiary's accounting software automatically — NetSuite, SAP, Dynamics, QuickBooks, etc. This is the cleanest setup.
  • File upload. The subsidiary's controller exports a TB from their system to CSV or Excel and uploads it to the consolidation app. The format usually has to match a defined template.
  • Web entry. For very small subsidiaries or non-financial entities, sometimes the data is keyed in directly.

In all cases, what arrives needs to be normalized into a common internal format before validation can run.

What validation checks

Once a TB is in the system, validation has to verify it's usable. Common checks:

Structural validation

  • Every row has a valid account code (exists in the local COA).
  • Every account code has a mapping to a group account, or routes to Suspense.
  • Required fields are present (amount, currency, period).
  • Amounts are numeric and within sane bounds (no clearly-wrong values like 999999999999).
  • The currency code matches the entity's expected functional currency.

Mathematical validation

  • The TB balances. Total debits equal total credits. If it doesn't, the data shouldn't be accepted.
  • Opening balances tie to last period's closing balances. Each balance sheet account's opening balance should equal what the same account had at the prior period close. See Lesson 2.3.
  • Sign conventions. Asset and expense accounts should have debit balances; liability, equity, and revenue accounts should have credit balances. Unusual signs (negative inventory? positive accumulated depreciation?) should at least raise a warning.

Business validation

  • Every expected subsidiary has submitted for the period.
  • Materially unusual variances from prior period flagged for review.
  • Subsidiary-level intercompany totals should agree to its counterparty's books within a tolerance.
  • Local-policy adjustments have been made (e.g., year-end accruals).

What happens on validation failure

The system has to decide what to do when a TB fails a check. There are three reasonable options, depending on severity:

SeverityBehavior
Critical (TB doesn't balance, no mapping at all)Reject the submission. Block this entity from progressing.
Error (unmapped account, missing required field)Accept but route problematic items to Suspense and surface them for resolution. Block period close until resolved.
Warning (unusual sign, large variance)Accept and flag for review. Don't block close, but record acknowledgment.

The principle: never let bad data flow silently through the pipeline. Every issue either gets resolved or gets explicitly acknowledged.

Standardizing TB format

Different subsidiaries submit TBs in different formats. Validation includes normalizing them all to the system's common shape. A typical internal representation:

Signed amounts vs. debit/credit columns

Conceptually, every transaction has a debit side and a credit side. In storage, it's common to use a single signed amount column where credits are negative. This avoids the awkwardness of having two columns where only one is ever populated per row.

The sign convention is usually: debit positive, credit negative. Then for any account:

  • Asset balance positive → normal (debit balance)
  • Liability balance negative → normal (credit balance)
  • Revenue balance negative → normal (credit balance)
  • Expense balance positive → normal (debit balance)

A trial balance balances when the sum of all signed amounts equals zero.

Why this matters for the software

For developers

The Ingest phase is the boundary between "the world's mess" and "our clean pipeline." Everything downstream assumes the data is well-formed. So this layer carries a lot of weight.

Three design principles that work well:

  • Fail loudly, fail early. A validation error caught at ingest is cheap; the same error caught at reporting is expensive (you have to back out every downstream step).
  • Capture rejections, don't drop them. Bad rows should be visible and resolvable, not silently discarded.
  • Make resubmission cheap. Subsidiaries will resubmit TBs many times during a typical close. Each resubmission needs to re-run validation cleanly and update the workflow state.

Summary

  • Each period, every subsidiary submits a trial balance — debits and credits, by account, in functional currency.
  • TBs arrive via integration, file upload, or web entry, in various formats.
  • Validation checks structure (fields, types), math (TB balances, opening ties to prior closing), and business sensibility (signs, variances, intercompany agreement).
  • Failures are categorized — critical (reject), error (Suspense + block), warning (flag).
  • Validated data lands in Local state, ready for currency translation.
