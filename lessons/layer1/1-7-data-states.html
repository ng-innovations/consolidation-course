Layer 1 — Lesson 7

Data states through the pipeline

The consolidation pipeline isn't just a sequence of operations — it's a sequence of data states. At each stage, the data sits in a particular, well-defined form. Each state has a name. Each transition between states is a specific phase of work.

This framing is more useful to developers than the traditional accounting-step framing, because it tells you exactly what data looks like at any point and what's been applied to it so far.

The six states

State 1: Local

This is the starting point — what we have after Phase B (Ingest) is complete.

What's true at this point:

  • Every subsidiary has submitted a trial balance for the period.
  • Each TB has been validated — it balances (debits equal credits), all required fields are present, accounts have been mapped to the group chart of accounts.
  • Each subsidiary's data is still in its own functional currency.
  • Nothing has been combined, eliminated, or adjusted.

You could think of this state as "every subsidiary's books, cleaned up and labeled consistently, but not yet touching each other."

State 2: Translated

After currency translation has been applied, every subsidiary's data is now in the group's presentation currency.

What changed:

  • Balance sheet accounts translated at the closing rate.
  • Income statement accounts translated at the average rate.
  • Equity accounts translated at historical rates.
  • The resulting differences captured as CTA within equity.

The data is still organized per subsidiary, but now all the numbers are comparable — they're all in the same currency.

State 3: Standardized

Group-level accounting policies have been applied. Any topside entries that need to happen before elimination are posted.

What changed:

  • Differences between local accounting policies and the group's are reconciled (e.g., bridges between local GAAP and IFRS).
  • Fair value adjustments at acquisition are recognized.
  • Goodwill is calculated and recorded.
  • Any other pre-elimination topside entries are booked.

The data is still per-entity but now reflects the group's accounting view of each entity, not just the local view.

State 4: Eliminated

Internal transactions between group entities have been removed.

What changed:

  • Intercompany AR matched and netted against intercompany AP.
  • Intercompany revenue matched and netted against intercompany expense.
  • Intercompany loans matched and netted against loans payable.
  • Unrealized profit on intercompany inventory transfers reversed.

This is the first state where the data starts looking truly "consolidated" — the entities are now combined and the internal noise is gone. What remains represents the group's transactions with the outside world.

State 5: Ownership-Adjusted

The math of who-owns-what has been applied.

What changed:

  • The parent's "Investment in Subsidiaries" line eliminated against subsidiaries' equity.
  • Non-controlling interest calculated for partially owned subsidiaries.
  • Net income split between "attributable to parent" and "attributable to NCI."
  • Equity properly split into "parent equity" and "NCI" components.

Now the data correctly represents not just the group's combined activity, but also who within the group (parent shareholders vs. outside shareholders of subsidiaries) is entitled to what portion of it.

State 6: Top (Final)

Final group-level adjustments — presentation reclassifications, last-minute audit adjustments, anything that needs to happen after all the math is done — are posted.

This is the data that gets used to produce reports. Once the period is locked, this is what gets snapshotted for audit.

Why naming the states matters

It makes the pipeline reasoning explicit

"After currency translation but before standardization" is a mouthful. "Translated state" is precise. When we discuss code, design docs, bug reports, or accounting issues, having shared vocabulary speeds everything up.

It clarifies dependencies

If someone asks "can we reverse this elimination?" — knowing that the elimination produces the Eliminated state from the Standardized state, we know exactly what needs to be redone. The dependencies are visible in the state diagram.

It supports drilldown design

A reported number in the Top state can be drilled back through each prior state, all the way to Local. The state model becomes the architecture of the drilldown.

It makes testing tractable

Each state transition can be tested independently. "Given data in state X, when transition Y is applied, the result should match expected state Z."

What "view as" means

In the application, users may be able to view the data at any of these intermediate states. A controller debugging a consolidated total might want to see "what did the numbers look like after translation but before standardization?" — that's a Translated-state view.

The product internally tracks the data at each state. Different reports might pull from different states. Different users might be empowered to make adjustments at different states.

The state, the operation, and the entry

One last clarification on terminology. Three concepts get confused in casual conversation but are distinct:

TermWhat it meansExample
StateA named form the data takes at a specific point in the pipeline"Eliminated"
OperationA pipeline action that transitions data from one state to the next"Currency translation"
EntryA specific journal entry posted during an operation"DR Cash $100; CR AR $100"

An operation produces many entries. Many entries together cause a transition from one state to the next. Each lesson in Layer 2 will be explicit about which operation it's covering and which state transition it produces.

Why this matters for the software

For developers

The data model in the application is designed around these states. Tables, views, and APIs are organized so that each state is queryable. Pipeline operations are designed as idempotent state transitions — given the same input state and the same configuration, they always produce the same output state.

When you read a piece of consolidation code, the first question to ask is: "what state does this assume the data is in, and what state does it leave the data in?" If you can answer those two questions, the rest of the code makes sense.

Summary

  • The consolidation pipeline produces a sequence of named data states: Local → Translated → Standardized → Eliminated → Ownership-Adjusted → Top.
  • Each state has a precise definition of what's been applied so far.
  • Operations (currency translation, elimination, etc.) are the transitions between states.
  • The state model supports reasoning about the pipeline, debugging numbers, designing drilldowns, and writing testable code.
